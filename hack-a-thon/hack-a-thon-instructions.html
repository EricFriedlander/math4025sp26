Hack-A-Thon Instructions

Artificial Intelligence Prologue

The grade for much of this assignment will be based on the accuracy of the predictions you generate on the test set. This is a relatively high-stakes assignment, and I want to be clear about the rules regarding the use of AI. It is expected that you don’t just following the literal instructions, but that you follow the spirit of the instructions. If you find yourself trying to find a “work-around” to these rules, that is a violation of the rules. If I suspect that you have violated the rules, I will investigate by reviewing your GitHub commit and, potentially, inviting you to explain your code during your “Job Interview” or during another time. If I find evidence of a violation, I will give you a zero on the assignment and may take further disciplinary action. If you have any questions about what is or is not allowed, please ask me before you do it. Moreover, you are expected to commit and push your code to GitHub regularly. If I suspect that you have violated the rules, I will check your commit history. If I see that all of your code was written and committed in a single big commit, you will receive a maximum of 50% on the assignment, regardless of your AI usage.

AI Rules

While I have been rather open to the use of AI in this class, the rules for this assignment are very strict. Please read carefully:

The following uses of AI are STRICTLY PROHIBITED:

  • Allowing any form of AI to see any of the data. This includes, but is not limited to, uploading the data to an AI platform. For example, you may not:
    • Upload the data to an LLM.
    • Copy an paste any output or summary statistics of your data into an LLM.
  • Using any form of agentic AI. For example, you may not use:
    • Claude Code, GitHub Copilot, OpenAI’s Codex, or any other AI that can see the context of your project and write code for you. It does not matter what capabilities you are using these tools for, if they can see the context of your project, you may not use them.
    • This includes the AI-augmented autocomplete features that are integrated in your code editor if you’re using GitHub Copilot or a similar tool.
  • Allowing any form of AI to see any of your results, the description of the project, or descriptions of the data. For example, you may not:
    • Paste any of your code, results, or descriptions into an LLM.
    • Copy and paste any of your code or any parts of the assignment instructions into an LLM.
    • Provide written descriptions of the data or project to an LLM in a way that would allow it to infer information about the data.
    • Provide a link to the course website to an LLM.
  • Having AI generate anything other than code (see below) that is eventually turned in to me.

The following uses of AI are PERMITTED as long as the restrictions are followed:

  • Using AI to help you write code, WITHOUT providing it any information about the context of the data. For example, you ask something like:
    • “Please generate Python code that generates a confusions matrix based on the output of a sklearn model.” This is fine, but if you were to add something like the names of the variables in your dataset, or any information about the project, that would be a violation of the rules. You may even use stand-in variable names (e.g. X_train, y_train, etc.) in your prompts, but you may not use the actual variable names or variable names that would give the AI any information about the context of the data.
    • “Generate a code snippet that takes a dataframe called X_test, generated predictions from a model called my_model, and writes the results to a files called my_predictions.csv.” This is ONLY ok, because X_test, my_model, and my_predictions.csv are all generic variable names that do not give the AI any information about the context of the data or project.
  • Use AI to help you brainstorm ideas for how to approach the project, WITHOUT providing it any information about the context of the data. For example, you ask something like: “What are some common approaches to multi-class classification problems?” This is fine, but if you were to add something like the names of the variables in your dataset, or any information about the project (like that it’s about finance), that would be a violation of the rules. You ARE welcome to look-up or google information about data analytics on financial data. However, you may not use AI in this aspect of the project.
  • You may use AI to help you debug your code. You MAY copy & paste error message as long as any references to variable names are removed or replaced. You are also allowed to copy & paste code that is causing the errors as long as you remove or replace the variable names.

GreenFin Capital: Loan Outcome Prediction

GreenFin Capital is a fintech startup that offers personal loans to borrowers who may not qualify for traditional bank financing. Unlike conventional lenders, GreenFin uses machine learning to evaluate applications in real time, aiming to extend credit responsibly to a broader population.

To do this well, GreenFin needs accurate models. An applicant who will repay on time should be approved and offered a competitive rate. An applicant who is likely to default should either be declined or offered a smaller loan. Making the wrong call in either direction costs the company money.

You’ve just joined GreenFin’s data science team. Your first assignment is to build a classifier that predicts the repayment outcome for each loan in a held-out test set.

Project Overview

GreenFin has provided two data files drawn from their historical lending records:

  • greenfin_train.csv contains 28,000 rows representing past loans, with 15 columns of borrower and loan characteristics, plus the outcome column loan_outcome.
  • greenfin_test.csv contains 12,000 rows with the same 15 feature columns, but loan_outcome has been withheld. These are the loans you must predict.

The target variable, loan_outcome, takes one of three values:

Value Meaning
0 On-Time — borrower repaid on schedule
1 Delinquent — borrower made payments, but repeatedly late
2 Default — borrower stopped making payments

You can find these datasets in the GitHub Classroom assignment.

Deliverables

There are two deliverables for this project:

  1. An HTML report or Jupyter Notebook walking through your final model. If using Quarto, push your .qmd source file and the rendered .html to the GitHub Classroom assignment. If using Jupyter Notebook, push the notebook. This is also where you can download the data files.

  2. A .csv file, pushed to your GitHub repository, containing your predictions for the 12,000 loans in the test set. Your file should have two columns: loan_id and loan_outcome, matching the loan IDs from greenfin_test.csv in the same row order, and be called my_predictions.csv. If it is not in this format, you will lose points. You can write this in Python with:

import pandas as pd

# df_test is your test dataframe; predictions is a list or array of 0s, 1s, and 2s
submission = pd.DataFrame({
    "loan_id": df_test["loan_id"],
    "loan_outcome": predictions
})
submission.to_csv("my_predictions.csv", index=False)

Your submission will be evaluated primarily on predictive accuracy — the fraction of test loans you correctly classify. Writing quality and depth of analysis are also assessed, as described below.

Not all columns in the data are immediately usable. You will need to handle non-numerical columns, address missing data, and think carefully about which features to include and how to represent them. Thoughtful feature engineering can substantially improve performance. Note that this data is is synthetic, but it is designed to reflect the kinds of challenges and patterns you would encounter in a real-world financial dataset.

Grading

Your submission will be graded across three components:

Component Weight
Predictive Accuracy 80%
Writing/Clarity 20%

Predictive accuracy is the primary criterion: your test accuracy will be compared against your classmates’ and graded accordingly. The writing /clarity component corresponds to how well you adhere to the Report Requirements.

Description of Variables

loan_id: A unique alphanumeric identifier assigned to each loan application. This column is provided for tracking purposes.

age: Age of the primary borrower in years at the time of application.

annual_income: Gross annual income reported by the borrower, in dollars.

employment_years: Number of years the borrower has been employed at their current job. Some borrowers did not report this, so the column contains missing values.

credit_score: FICO credit score at the time of application, ranging from 300 (poor) to 850 (excellent).

loan_amount: Total loan amount requested, in dollars.

loan_term_months: Agreed repayment term in months. Takes one of five values: 12, 24, 36, 48, or 60.

debt_to_income: The ratio of the borrower’s total monthly debt payments to their gross monthly income, expressed as a decimal (e.g., 0.25 means 25%). Also called DTI.

num_credit_lines: Number of open credit accounts on the borrower’s credit report at application time. Some values are missing.

num_late_payments: Number of late payments recorded on the borrower’s credit report in the 24 months prior to application.

has_mortgage: Whether the borrower currently holds a mortgage. Encoded as 1 (yes) or 0 (no).

home_ownership: The borrower’s current housing situation. Takes one of three values: Own, Rent, or Mortgage.

loan_purpose: The stated primary purpose of the loan. Takes one of five values: Debt Consolidation, Home Improvement, Education, Business, or Other.

state_region: Geographic region of the borrower’s primary address. Takes one of five values: Northeast, Southeast, Midwest, Southwest, or West.

monthly_obligations: The borrower’s total recurring monthly debt obligations in dollars, not counting the new GreenFin loan.

Report Requirements

General Guidelines

  • ONLY INCLUDE STEPS THAT MADE IT INTO YOUR FINAL MODEL. DO NOT INCLUDE MODELS OR STEPS THAT YOU TRIED BUT DECIDED AGAINST.
  • Keep the written parts of your submitted report extremely short.
  • All prose should be concise and written in bulleted lists.
  • Your report should be formatted as a Jupyter notebook or qmd file. Note that I should be able to run it from top-to-bottom without an error.
  • Note that you should be running a lot of code (e.g. data exploration) that should not be included in your final report.

Report Structure

Include the following sections. For each section you should create a markdown header (e.g. ## Data Cleaning) and then include the required content for that section. The sections should be in the following order and include the following information:

  1. Loading python packages and the data (2 code blocks)
    • Code block 1: load all of the packages your use in your analysis. Note that any packages you use in your code MUST be loaded here.
    • Code block 2: load the data. You should load both the training and test data here.
  2. Data Cleaning and Feature Engineering (1 bulleted list and 1 code block)
    • Bulleted list of the data cleaning steps you took and a VERY brief explanation for why. For examples, what variables did you remove, what new variables did you create, etc.
    • Code block: All the code that executes those steps. Any Pipelines and ColumnTransformers should go in the next section. Note: You SHOULD be making plots of your data, but do not include them in your final report.
  3. Pre-processing (1 bulleted list and 1 code block)
    • Bulleted list of the pre-processing steps you took and a VERY brief explanation for why.
    • Code block: All the code for those steps. This is where any Pipelines and ColumnTransformers should go in this section.
  4. Model Fit and Tuning (1 bulleted list and 2 code blocks)
    • Bulleted list: Your list should include the following information:
      • Any splitting or cross-validation strategy you used to evaluate your model. DO NOT INCLUDE THE cross-validation code, just a description of what you did.
      • All the types of models you tried and the one you ultimately chose for your final model.
      • All the hyperparameters you tuned for your final model and how you tuned them. If you used a tool like GridSearchCV or RandomizedSearchCV, DO NOT INCLUDE THESE. Instead, just fit the model with the optimal hyperparameters that you found with these tools.
    • Code block 1: A code block that includes all of the code preparing to fit and tune ONLY YOUR FINAL MODEL. Do not include code for models you tried but ultimately decided against. Do not include code for tuning hyperparameters. Do not include cross-validation or model evaluation.
    • Code block 2: The line or lines of code that actually fit your final model. This is the only code cell that should take a long time to execute.
  5. Prediction Generation: (1 code block)
    • A code block that includes the code for generating the predictions for the test set and writing the results to a my_predictions.csv file.
